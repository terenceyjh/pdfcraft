# 同一 PDF 的双窗口阅读与同步编辑

日期：2026-10-21。目标：同一 PDF 同时在两个原生窗口中阅读不同章节，分别批注，修改立即互相可见。

## 实现方向

采用单进程、一份 Session/Document、多个独立窗口视图。窗口共享文档对象、编辑历史、脏状态及保存目标；各自拥有导航、缩放、滚动、选区、工具、编辑草稿及渲染队列。避免复制 PDF 后依靠磁盘重载同步，以免覆盖尚未保存的笔记。

备选方案是多进程通过磁盘或 IPC 同步；它需要处理并发版本冲突、加密文档和保存竞争，本期不采用。

本期提供第二个窗口入口，重复操作聚焦已有窗口。数据组织不依赖固定的左右两栏，后续可扩展到更多窗口。

## 验收场景

- 打开多页 PDF，在第二窗口打开同一文档；两边可停留在不同页，滚动与缩放互不影响。
- 两边依次添加/修改笔记，另一边可在对应页面立即看到，不必保存或重新打开。
- 撤销、重做及保存针对共享文档；另存为后两边仍指向同一文档。
- 关闭任意一个阅读窗口不丢弃另一窗口的工作；最后关闭文档时仍提示保存。
- 无文件路径或加密的已打开文档不需要重新读取或再次输入密码。
- 第二窗口已经存在时再次打开不会创建互不相干的文档副本。

## 使用方法

打开 PDF 后，从「视图 → 在新窗口中打开」或文档标签的右键菜单打开第二阅读窗口。
第二窗口可以单独翻页、缩放、搜索、使用批注工具，并打开批注、书签或缩略图面板。
已发布的批注、绘画、表单修改和撤销/重做实时作用于同一份文档；两边的保存和另存为操作使用同一个保存目标。
尚在输入框中的批注需要先发布或取消，关闭保护会保留这些草稿。

普通 File → Open 和 `--new-window` 的既有行为保持不变；共享编辑通过上面的专用入口使用。

真实原生窗口验证使用项目内临时生成的四章 PDF，不使用用户文档：

- 主窗口停第 1 章、第二窗口停第 3 章，页码及缩放独立。
- 两边分别通过真实批注输入框发布笔记，另一窗口立即读到，共 2 条。
- 在第二窗口保存、主窗口撤销、第二窗口重做，共用同一份历史；独立 CLI 重新打开保存文件确认 2 条批注完整。
- 关闭主标签后第二窗口仍能操作；再次打开文件复用同一个 DocId，没有重新创建文档副本。
- 隐藏主窗口后第二窗口继续响应；“显示主窗口”能恢复主窗口。
- 关闭第二窗口保留主文档；重复打开聚焦已有第二窗口。
- 实际输入未发布的主窗口笔记后，隐藏和退出均被阻止；清理测试草稿后文档仍只有已保存的 2 条笔记。

调试中定位并修复：

1. 两个视图不能共用单消费者渲染队列，否则互相取消任务或消费结果。
2. 控件、搜索框、批注输入框需要独立身份，同时保留主窗口原有身份，避免旧功能回归。
3. egui 在输出回调前已恢复父视口；控制通道要配对原始输入中的视口身份。
4. 文件监听、恢复快照与保存目标必须随共享文档一起借用，避免第二窗口绕过外部文件覆盖保护或残留已保存的恢复副本。
5. 最后一个窗口退出仍要保护未发布草稿；被拒绝的表单提交也要先取消原生关闭事件。
6. 阅读颜色等渲染配置会改变文档版本而不替换 PDF 字节，因此渲染器同时追踪版本与字节身份。通过比较实际渲染像素验证。

输入隔离、最后退出草稿保护、渲染配置刷新三个回归均实际观察过修复前失败、修复后通过。
临时运行记录、测试 PDF 和截图位于 `target/qa/`，已被忽略，不进入产品资源或提交。

## 构建与调试

```powershell
. ./dev-env.ps1 -Proxy
cargo build -p pdfcraft -j 2
./target/debug/pdfcraft.exe book.pdf
```

`-Proxy` 仅为本 shell 的 Cargo 与 GitHub 下载启用 `127.0.0.1:10819`；所有 Rust 文件在项目 `.tools`，输出在 `target`。
原生验证采用便携标记 `target/debug/portable.txt`，设置与恢复数据也保留在项目的 `target/debug/PdfCraftData`。

控制通道仍需显式 `--control FILE` 启用。新增 `ui.window` 的 `state/open/set/command/close/hide-primary` 操作；输入、检查与状态请求可用 `window=<DocId>` 指定第二窗口。
第二窗口的 `set` 面向阅读视图选项；全局应用偏好在主窗口设置。

## 本期边界

- 每份 PDF 支持两个共享视图；多视图选择与窗口位置/阅读位置的跨重启恢复留给后续版本。
- 第二窗口提供阅读、搜索和批注常用工具；完整工具面板仍在主窗口。
- 已发布修改立即共享；尚未发布的输入草稿保留在各自窗口，关闭时需先发布或取消。
- 独立进程的 `--new-window` 不参与此共享会话。
- eframe 0.36.2 的 immediate/WGPU 路径不处理第二窗口截图命令。`ui.screenshot window=...` 明确返回不支持；主窗口内置截图正常。系统窗口抓图工具重试后仍超时，因此第二窗口视觉检查使用实际渲染完成后的界面回归图，并结合原生窗口界面树与渲染状态。该限制只影响调试截图，不影响阅读或批注。
